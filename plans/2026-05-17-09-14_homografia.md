# Homografía de pista de padel

## ¿Qué es la homografía en este contexto?

Una **homografía** es una transformación proyectiva que relaciona dos planos. En este proyecto la usamos para mapear puntos del frame de vídeo (píxeles `[u, v]`) a coordenadas reales sobre el plano de la pista (metros `[x, y]`).

La pista de padel tiene dimensiones estándar: **10 m × 20 m**. El origen de coordenadas se fija en una esquina conocida (por convención, la esquina trasera izquierda desde la perspectiva de la cámara).

```
Imagen (píxeles)          Plano real (metros)
                               0        10
    ┌──────────┐          0  ┌────────────┐
    │  [u, v]  │    H       │  [x,  y]   │
    │          │  ──────►   │            │
    └──────────┘         20 └────────────┘
```

La transformación se expresa como:

```
[u]       [x]         [h₁₁ h₁₂ h₁₃]   [x]
[v]  = H  [y]    con  [h₂₁ h₂₂ h₂₃] × [y]
[1]       [1]         [h₃₁ h₃₂ h₃₃]   [1]
```

La matriz H tiene 8 grados de libertad (se normaliza a escala 1), por lo que se necesitan **mínimo 4 correspondencias de puntos** para calcularla.

---

## Proceso general de cálculo

Independientemente del método usado para obtener las correspondencias, los pasos posteriores son siempre los mismos.

### Paso 1 — Recopilar correspondencias

Obtener N pares de puntos `(p_img, p_real)` donde:
- `p_img = [u, v]` — posición en píxeles en el frame.
- `p_real = [x, y]` — posición conocida en metros sobre la pista.

Los puntos de referencia naturales son intersecciones de líneas de la pista:

| ID | Descripción                    | Coordenada real (x, y) |
|----|--------------------------------|------------------------|
| A  | Esquina trasera izquierda      | (0, 0)                 |
| B  | Esquina trasera derecha        | (10, 0)                |
| C  | Esquina delantera izquierda    | (0, 20)                |
| D  | Esquina delantera derecha      | (10, 20)               |
| E  | Línea central trasera, iz.     | (0, 10)                |
| F  | Línea central trasera, der.    | (10, 10)               |
| G  | Intersección red–línea central | (5, 10)                |
| H  | Intersección central–lateral iz| (0, 13)                |
| …  | …                              | …                      |

Cuantas más correspondencias, más robusta la estimación. Se recomienda un mínimo de 6–8.

### Paso 2 — Calcular H con DLT + RANSAC

El algoritmo **DLT (Direct Linear Transform)** plantea un sistema lineal sobredeterminado a partir de las correspondencias y lo resuelve por **SVD** (descomposición en valores singulares). En la práctica se usa la implementación de OpenCV:

```python
import cv2
import numpy as np

pts_img  = np.array([[u1,v1], [u2,v2], ...], dtype=np.float32)
pts_real = np.array([[x1,y1], [x2,y2], ...], dtype=np.float32)

H, mask = cv2.findHomography(pts_img, pts_real, method=cv2.RANSAC, ransacReprojThreshold=0.5)
```

El flag `RANSAC` descarta automáticamente correspondencias ruidosas (outliers). `ransacReprojThreshold` es el error máximo en píxeles para considerar un punto como inlier.

### Paso 3 — Validar con error de reproyección

El **error de reproyección** mide cuántos píxeles se aleja la estimación de la posición real conocida:

```python
def reprojection_error(H, pts_img, pts_real):
    pts_img_h = np.hstack([pts_img, np.ones((len(pts_img), 1))])
    projected = (H @ pts_img_h.T).T
    projected /= projected[:, 2:3]
    return np.mean(np.linalg.norm(projected[:, :2] - pts_real, axis=1))
```

Un error < 0.05 m (5 cm) es aceptable para este caso de uso.

### Paso 4 — Aplicar la transformación

Con H calculada, transformar cualquier punto de la imagen al plano real:

```python
def to_court_coords(H, u, v):
    p = np.array([u, v, 1.0])
    q = H @ p
    return q[0] / q[2], q[1] / q[2]  # (x_metros, y_metros)
```

## Enfoques para obtener las correspondencias

### Enfoque A — Selección manual de puntos

El usuario indica manualmente en un frame de referencia qué píxel corresponde a cada punto conocido de la pista.

**Implementación**:
```python
import cv2

points = []

def on_click(event, u, v, flags, param):
    if event == cv2.EVENT_LBUTTONDOWN:
        points.append((u, v))

cap = cv2.VideoCapture("video.mp4")
ret, frame = cap.read()

cv2.namedWindow("Seleccionar puntos")
cv2.setMouseCallback("Seleccionar puntos", on_click)

while True:
    display = frame.copy()
    for i, (u, v) in enumerate(points):
        cv2.circle(display, (u, v), 5, (0, 255, 0), -1)
        cv2.putText(display, str(i), (u+5, v-5), cv2.FONT_HERSHEY_SIMPLEX, 0.5, (0,255,0), 1)
    cv2.imshow("Seleccionar puntos", display)
    if cv2.waitKey(1) == ord('q'):
        break
```

El usuario hace click sobre las intersecciones de líneas en el orden predefinido, y esos píxeles se emparejan con las coordenadas reales conocidas.

**Pros**: Simple de implementar, muy preciso si el usuario es cuidadoso, sin dependencias de ML.  
**Contras**: Requiere intervención humana. Si la cámara se mueve hay que repetirlo.

### Enfoque B — Detección clásica de líneas (Hough)

Detectar las líneas de la pista automáticamente con visión clásica y extraer sus intersecciones.

**Implementación**:
```python
import cv2
import numpy as np

def detect_court_lines(frame):
    gray = cv2.cvtColor(frame, cv2.COLOR_BGR2GRAY)
    blur = cv2.GaussianBlur(gray, (5, 5), 0)
    edges = cv2.Canny(blur, threshold1=50, threshold2=150)

    # Detectar líneas largas (las de la pista son largas y rectas)
    lines = cv2.HoughLinesP(edges, rho=1, theta=np.pi/180,
                             threshold=100, minLineLength=100, maxLineGap=20)
    return lines

def line_intersection(l1, l2):
    # Calcular intersección de dos segmentos en coordenadas homogéneas
    x1,y1,x2,y2 = l1; x3,y3,x4,y4 = l2
    a = np.cross([x1,y1,1], [x2,y2,1])
    b = np.cross([x3,y3,1], [x4,y4,1])
    pt = np.cross(a, b)
    if abs(pt[2]) < 1e-8:
        return None  # paralelas
    return pt[0]/pt[2], pt[1]/pt[2]
```

Las líneas detectadas se clasifican por orientación (horizontales = líneas de fondo/red, verticales = laterales) y se calculan sus intersecciones para obtener los puntos de referencia.

**Pros**: Sin necesidad de datos de entrenamiento ni intervención humana.  
**Contras**: Frágil ante variaciones de iluminación, sombras, oclusiones de jugadores. Las líneas de la pista de padel son a veces poco visibles por el suelo de resina o el polvo.

### Enfoque C — Detección de keypoints con deep learning

Entrenar o usar un modelo de estimación de poses para detectar directamente las intersecciones de la pista como keypoints.

**Implementación con YOLO-pose**:
```python
from ultralytics import YOLO

# Modelo YOLO-pose fine-tuneado para detectar keypoints de pista de padel
model = YOLO("court_keypoints.pt")

results = model(frame)
keypoints = results[0].keypoints.xy[0]  # shape: [N_keypoints, 2]

# keypoints[0] = esquina trasera izquierda, keypoints[1] = esquina trasera derecha, ...
pts_img = keypoints.cpu().numpy()
```

**Dataset requerido**: ~500–2000 imágenes de pistas de padel anotadas con los keypoints de las intersecciones. Se puede partir de un modelo YOLO-pose preentrenado en tenis (court keypoints) y hacer fine-tuning.

**Pros**: Robusto a cambios de iluminación, oclusiones parciales, diferentes tipos de pista.  
**Contras**: Requiere recolectar y anotar datos de entrenamiento. Mayor coste computacional en inferencia.

### Enfoque D — Marcadores físicos (ArUco / ChArUco)

Colocar marcadores visuales (ArUco tags) en posiciones conocidas de la pista. OpenCV los detecta automáticamente con alta precisión.

**Implementación**:
```python
import cv2

aruco_dict = cv2.aruco.getPredefinedDictionary(cv2.aruco.DICT_4X4_50)
detector = cv2.aruco.ArucoDetector(aruco_dict)

corners, ids, _ = detector.detectMarkers(frame)

# Emparejar IDs con coordenadas reales conocidas
real_coords = {0: (0,0), 1: (10,0), 2: (0,20), 3: (10,20)}  # ID → (x,y) en metros

pts_img, pts_real = [], []
for i, marker_id in enumerate(ids.flatten()):
    if marker_id in real_coords:
        center = corners[i][0].mean(axis=0)  # centro del marcador en píxeles
        pts_img.append(center)
        pts_real.append(real_coords[marker_id])
```

Un tablero **ChArUco** combina un damero de calibración con marcadores ArUco, lo que permite también calibrar la distorsión de la cámara además de la homografía.

**Pros**: Muy alta precisión, detección completamente automática en tiempo real.  
**Contras**: Requiere colocar marcadores físicos en la pista antes de grabar. No funciona con vídeos ya existentes.

### Enfoque E — Calibración con modelo 3D de la pista

En lugar de asumir que todo ocurre en un plano 2D, modelar la pista en 3D con las dimensiones reales y resolver la pose de la cámara (posición + rotación) con `solvePnP`.

**Implementación**:
```python
import cv2
import numpy as np

# Puntos 3D de la pista (z=0 para el suelo)
pts_3d = np.array([
    [0, 0, 0], [10, 0, 0], [10, 20, 0], [0, 20, 0],  # esquinas
    [0, 10, 0], [10, 10, 0],                           # línea central
], dtype=np.float32)

# Puntos 2D correspondientes en la imagen (en píxeles)
pts_2d = np.array([[u1,v1], [u2,v2], ...], dtype=np.float32)

# Matriz de cámara (focal length + centro óptico)
K = np.array([[fx, 0, cx], [0, fy, cy], [0, 0, 1]], dtype=np.float32)
dist = np.zeros(5)  # distorsión (corregir antes si la lente es gran angular)

success, rvec, tvec = cv2.solvePnP(pts_3d, pts_2d, K, dist)

# Para proyectar: H = K * [R | t] (aproximación planar)
```

Este enfoque permite proyectar correctamente objetos que están a distintas alturas (la bola en el aire), algo que la homografía pura no puede hacer sin información adicional.

**Pros**: Más preciso para objetos fuera del plano del suelo (pelota en el aire). Permite estimar la altura real de la bola.  
**Contras**: Requiere conocer la matriz intrínseca de la cámara (calibración previa con tablero de damero). Significativamente más complejo.

## Conclusión

Para este proyecto, la cámara es **estática** y el ángulo de visión es conocido (vista desde el lateral/fondo de la pista). Esto simplifica considerablemente el problema.

### Recomendación

**Para empezar**: Enfoque A (manual), usando una pequeña interfaz de selección de puntos. Requiere menos de una hora de implementación, funciona con cualquier vídeo y da la homografía más precisa posible. Es la referencia perfecta para validar los demás enfoques.

**Para producción**: Enfoque C (YOLO-pose) es el balance óptimo entre automatización, robustez y coste. Con un dataset de ~1000 imágenes de pistas de padel anotadas se puede fine-tunear un modelo preentrenado en pocas horas de GPU.

**Si se controla el entorno de grabación**: Enfoque D (ArUco) da la mejor precisión completamente automática, con el único coste de colocar 4 marcadores en las esquinas antes de grabar.

El enfoque E solo merece la pena si se necesita estimar la **altura real de la pelota** (para análisis de bote o velocidad 3D), ya que la complejidad adicional no aporta mejoras en la detección de zona 2D.
