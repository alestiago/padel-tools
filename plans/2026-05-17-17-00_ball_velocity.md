# Plan — Detector de velocidad de pelota (punto 2)

## Dependencias

- **[7] Posición de la bola por frame** — necesitamos saber dónde está la pelota en píxeles.
- **[1] Homografía H** — ya existe como `homography-tool` y exporta `homography_video.json`.

El cálculo en sí es trivial una vez resueltas estas dependencias:

```
v (m/s) = dist_real(p_t, p_{t+1}) / (1 / fps)
v (km/h) = v × 3.6
```

Suavizado: ventana deslizante de 3–5 frames para eliminar ruido de detección.

## Opciones de implementación

### Opción A — Nueva Vite app independiente (`ball-velocity-tool`) ★ RECOMENDADA

Una app React/Vite separada, hermana de `homography-tool`. El usuario carga:
1. El vídeo original.
2. El JSON de homografía exportado por `homography-tool`.

La app ejecuta el detector de bola en el navegador vía ONNX Runtime Web (ya presente en el stack) y calcula la velocidad frame a frame.

```
padel_tools/
├── homography-tool/      ← ya existe
├── ball-velocity-tool/   ← nueva (misma base: Vite + React + TS + Tailwind + onnxruntime-web)
└── plans/
```

**Flujo de usuario:**
1. Abrir `ball-velocity-tool`.
2. Cargar vídeo + `homography_video.json`.
3. La app recorre los frames, infiere la posición de la bola con el modelo ONNX, calcula velocidad.
4. Overlay en vídeo: posición de la bola + velocidad en km/h.
5. Exportar CSV o JSON con velocidad por frame (para usarlo en el algoritmo de corte final).

**Pros:**
- Mantiene cada herramienta pequeña y enfocada.
- `homography-tool` ya está terminada — no la toca.
- El JSON de homografía es el contrato limpio entre herramientas.
- `onnxruntime-web` ya está en el stack.
- Fácil de iterar en aislamiento.

**Contras:**
- Duplica el boilerplate de Vite/React.
- El usuario tiene que gestionar dos apps separadas y pasar el JSON manualmente.

---

### Opción B — Ampliar `homography-tool` con una segunda fase

Añadir una nueva pantalla/pestaña dentro de la app existente. Después de establecer la homografía (fase 1), el usuario avanza a la fase de detección de velocidad (fase 2).

**Pros:**
- UX unificada: un solo flujo paso a paso.
- No hay que pasar el JSON manualmente; H se pasa en memoria.
- No hay duplicación de boilerplate.

**Contras:**
- La `homography-tool` pasa de ser una herramienta de anotación de puntos a convertirse en una app de análisis de vídeo — responsabilidades muy distintas.
- Añade peso (el modelo ONNX de detección de bola es grande) a una app que hoy es muy ligera.
- Complica el árbol de componentes de una app que ya funciona.
- A medida que se añadan puntos 3, 4, 5... la app se convierte en un monolito difícil de mantener.

---

### Opción C — Script Python (sin web UI)

Un script Python que usa OpenCV + el modelo de detección para procesar el vídeo y escribir un CSV con velocidad por frame. Sin interfaz gráfica.

**Pros:**
- Las bibliotecas de CV de Python son maduras (OpenCV, PyTorch, Ultralytics).
- TrackNetV2 tiene implementación oficial en Python.
- Más rápido de prototipar la lógica pura.

**Contras:**
- Rompe el paradigma "todo en el navegador" del proyecto.
- Requiere que el usuario tenga Python, dependencias y GPU configurados.
- No da feedback visual inmediato.
- No encaja con el resto del stack (Vite/React/TS).

---

## Recomendación: Opción A

**Nueva Vite app.** Misma base que `homography-tool` (Vite + React + TS + Tailwind + `onnxruntime-web`). Las razones decisivas:

1. La `homography-tool` tiene una responsabilidad clara (anotar puntos, calcular H) — no mezclar.
2. `onnxruntime-web` ya está probado en el stack.
3. La separación por herramientas escala bien para los puntos 3–7 del action plan.
4. El JSON de homografía ya existe como formato de intercambio.

Cuando haya 3–4 herramientas maduras se puede plantear una app unificada tipo "wizard" multi-paso; hacerlo ahora sería prematuro.

## Detector de bola: opciones de modelo ONNX

El cuello de botella real es el punto [7]: detectar la posición de la bola por frame.

### Modelo A — YOLOv8n fine-tuneado (recomendado para empezar)

- **Entrada**: un frame RGB.
- **Salida**: bounding boxes con clase "ball".
- **ONNX**: exportación directa con `model.export(format="onnx")`.
- **Tamaño**: ~6 MB.
- **Pipeline sencillo**: un frame → una inferencia → coordenadas.
- **Dataset**: ~500–1000 imágenes de pelotas de padel/tenis con anotación de bbox.
- **Limitación**: puede perder la bola en frames con movimiento rápido (motion blur).

### Modelo B — TrackNetV2 (mejor tracking, más complejo)

- **Entrada**: 3 frames consecutivos apilados (9 canales).
- **Salida**: heatmap 2D con la posición de la bola.
- **ONNX**: el modelo original es PyTorch; exportable a ONNX.
- **Tamaño**: ~12 MB.
- **Ventaja clave**: diseñado para pelotas de raqueta en movimiento rápido; robusto ante blur.
- **Limitación**: pipeline más complejo (buffer de 3 frames, postproceso del heatmap).

### Modelo C — Detección clásica (blob detection, sin ML)

- Color filtering (amarillo/verde de la pelota) + blob detector de OpenCV.
- Sin modelo, sin ONNX. Implementable con `opencv-js` en el navegador.
- Muy frágil ante variaciones de iluminación y fondos similares al color de la pelota.
- Útil como baseline rápido para validar la fórmula de velocidad.

**Recomendación de modelo**: empezar con **Modelo C (clásico)** para validar la fórmula de velocidad con la homografía real, luego iterar a **Modelo A (YOLOv8n)** para robustez, y plantearse **Modelo B (TrackNetV2)** si la tasa de detección sigue siendo insuficiente.

## Pasos de implementación (Opción A + secuencia de modelos)

1. **Scaffold** `ball-velocity-tool` con `npm create vite@latest` — React + TS. Añadir Tailwind y `onnxruntime-web`.
2. **UI base**: carga de vídeo y carga de `homography_video.json`.
3. **Frame extractor**: usar `<canvas>` + `requestVideoFrameCallback` para extraer frames.
4. **Fase 1 — validación con blob detection clásico** (`opencv-js`): detectar pelota, aplicar H, calcular velocidad. Overlay en vídeo.
5. **Fase 2 — YOLOv8n ONNX**: sustituir el detector clásico por inferencia ONNX. Comparar resultados.
6. **Fase 3 — TrackNetV2 ONNX** (opcional): mejorar tracking si YOLOv8n no es suficiente.
7. **Exportación**: CSV/JSON con `[frame, timestamp, px, py, x_real, y_real, velocity_kmh]`.

## Notas técnicas

- **`requestVideoFrameCallback`**: API moderna del navegador para procesar frames al ritmo exacto del vídeo. Disponible en Chrome/Edge; Safari desde 15.4.
- **Worker thread**: la inferencia ONNX debe correr en un Web Worker para no bloquear el hilo principal.
- **Homografía en JS**: la transformación `H * [u, v, 1]ᵀ` es una multiplicación de matrices 3×3 — implementable en 10 líneas sin dependencias. No hace falta importar OpenCV para esto.
- **Smoothing**: media móvil de 5 frames sobre la velocidad calculada.
- **FPS del vídeo**: extraer con `video.playbackRate` y `video.duration / video.seekable`.
